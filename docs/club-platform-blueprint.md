# 球團平台藍圖（Club Platform Blueprint）

> 版本：草案 v0.1 · 2026-10-01 · 基準 commit `a60560d`
> 用途：定義足球球團「應該有」的功能與架構，作為之後拆 spec、交給 cloud agent 實作的母文件。
> 原則：單一球團、數百位使用者、一人維運。Roadmap 是看見選項與決策點的工具，不是甘特圖；實際使用資料和這份規劃矛盾時，改規劃。

---

## 0. 現況工作模式與痛點

| 面向 | 現況（人工） | 痛點 |
| --- | --- | --- |
| 課程 | 一次購買 10／20／30 堂，球團發實體課程卡，每次上課在卡上記日期 | 卡片會遺失、無法遠端查剩餘堂數、對帳要翻卡 |
| 出席 | 不強制出席、無效期，來了就登記 | 沒有預先報名人數，教練不知道今天會來幾人 |
| 金流 | 匯款與現金都由人工確認、手寫或試算表紀錄 | 匯款要逐筆比對；現金沒有收據與日結 |
| 賽事 | 同一位工作人員負責報名、廣播、佈達、提醒 | 工作散在 LINE 群組與腦中，沒有清單，容易漏 |
| 語言 | 同一位工作人員即時翻譯日本教練的訊息 | 翻譯佔用大量時間，且是單點依賴 |

**設計目標：** 把「人記得」換成「系統列出來」，把「人做」換成「AI 擬稿、人確認」。

## 1. 系統全貌

```
┌──────────────────────── 觸點層 ────────────────────────┐
│ 官方網站（公開）       LINE 官方帳號 + Rich Menu        │
│                        └ LIFF 頁面（家長／教練）         │
│ 營運後台（管理員 Web）  行事曆訂閱（Google / Apple）     │
└───────────────────────────┬────────────────────────────┘
┌──────────────────────── 業務核心 ───────────────────────┐
│ ① 身分與家戶   ② 季度與在籍   ③ 排程與出勤             │
│ ④ 帳務（堂數錢包、收款、對帳） ⑤ 賽事                  │
│ ⑥ 溝通（公告、提醒、翻譯）    ⑦ 內容（官網 CMS、名單） │
│ ⑧ 工作清單（Task Inbox）                               │
└───────────────────────────┬────────────────────────────┘
          audit_log ＋ outbox（同一筆交易內寫入）
                            │
┌──────────────────────── 自動化層 ───────────────────────┐
│ 規則引擎（排程、門檻）   AI 助理（擬稿、翻譯、擷取）     │
│ 一律「AI 擬稿 → 人確認」，金流與對外發送不全自動         │
└────────────────────────────────────────────────────────┘
```

技術棧維持 Next.js + Supabase（RLS + RPC 是唯一真相）。新增：LINE Messaging API、LIFF、Claude API、Vercel Cron。**不**新增微服務、訊息佇列或原生 App。

### 2.2 LINE 官方帳號 + LIFF（家長與教練的主要入口）

**為什麼是 LINE 而不是 App／PWA：** 台灣與在台日籍家長都已在用 LINE；不需安裝；LIFF 可直接取得 LINE 身分，省掉 SMS OTP 費用與「加到主畫面」的門檻。

**身分整合：** LINE Login（LIFF）取得 `line_user_id` → 綁定到 `profiles`。第一次使用時仍需驗證（邀請碼，見 §3.1），之後免登入。現有 SMS OTP 保留給管理員後台與沒有 LINE 的少數人。

**Rich Menu（家長版）：**

| 按鈕 | LIFF 頁面 | 內容 |
| --- | --- | --- |
| 我的課程卡 | `/liff/card` | 數位課程卡：剩餘堂數、每次上課日期（取代實體卡）、購買紀錄 |
| 行事曆 | `/liff/calendar` | 孩子所屬梯隊的訓練與賽事；一鍵訂閱到 Google／Apple |
| 賽事回覆 | `/liff/matches` | 待回覆的召集（可出賽／不行），截止時間 |
| 請假／留言 | `/liff/leave` | 告知今天不來（非必要，只是幫教練估人數） |
| 繳費回報 | `/liff/pay` | 選方案 → 上傳轉帳截圖（AI 擷取金額與末五碼）→ 送出 |
| 聯絡球團 | 聊天 | 進入 LINE 對話，由 AI 先分類（§4） |

**Rich Menu（教練版，依角色切換）：**

| 按鈕 | 內容 |
| --- | --- |
| 今日點名 | 今天的場次 → 名單一鍵勾選出席（扣堂）；未在名單者可搜尋加入 |
| 賽事名單 | 召集回覆狀況、確定名單、背號 |
| 球員評估 | 日文或中文填寫，系統自動翻譯給家長（§4） |
| 發公告 | 用母語輸入 → AI 翻成三語 → 確認後發送 |

### 2.3 營運後台（管理員 Web）

沿用現有 `/app/admin/**`，加上：工作清單首頁（§3.8）、收款與對帳、現金日結、CMS、潛在學員、AI 草稿審核區。

### 2.4 行事曆訂閱

- 每位家長、每位教練、每個梯隊／隊伍各有一條 **ICS feed**：`/api/cal/{token}.ics`，token 隨機產生、可撤銷重發。
- 家長 feed ＝ 名下所有孩子的梯隊與隊伍；教練 feed ＝ 指派的隊伍；梯隊 feed（公開版）只含已發布賽事，不含任何個資。
- 在 LIFF 提供「加入 Google 行事曆」（`webcal://` 轉 Google 訂閱網址）與「加入 Apple 行事曆」（`webcal://`）兩顆按鈕。
- 注意：Google 對訂閱行事曆的更新頻率由 Google 控制（可能數小時），**臨時異動仍要靠 LINE 推播**；行事曆是「看得到」，LINE 是「通知到」。
- 現有 `lib/org/calendar-export.ts` 已能產生單一 VEVENT，可擴充為多事件 feed（新增 `app/api/cal/[token]/route.ts`）。

### 2.5 是否需要原生 App

**現在不做。** 決策點：當出現以下任一情況再評估——
- 教練在球場網路不穩，需要離線點名；
- 球員（U13 以上）需要自己的帳號與訓練紀錄；
- LINE 的訊息費用或 LIFF 限制成為瓶頸。

在那之前，LIFF + PWA 已涵蓋家長與教練所需。

## 3. 業務模組

### 3.1 身分與家戶

| 實體 | 說明 |
| --- | --- |
| `households` | 家戶：付款、通知與同意的單位；兄弟姊妹同一戶 |
| `household_members` | 家長（主要／次要）、緊急聯絡人 |
| `players` | 現有；掛在家戶下 |
| `line_identities` | `line_user_id` ↔ `profile_id` |
| `invite_codes` | 每位球員一次性邀請碼；輸入碼＋孩子生日即完成綁定（取代開放搜尋，修正簡報 R1） |
| `consents` | 個資告知版本、肖像授權、證件用途；誰、何時同意 |
| `medical_notes` | 過敏、病史；只有管理員與該隊教練可讀 |

### 3.2 季度與在籍

| 實體 | 說明 |
| --- | --- |
| `seasons` | 每年 8/15 起算 |
| `enrollments` | 球員 × 季度：體驗／在籍／暫停／離隊 |
| 換季工具 | 管理員一鍵批次升組，先看預覽再執行（2027-08-15 前完成） |

### 3.3 排程與出勤（**配合「自由出席」模式調整**）

現況的實際做法是「來了就登記」，所以系統的核心動作應該是**簽到**，不是**報名**：

| 動作 | 訓練 | 賽事 |
| --- | --- | --- |
| 事前回覆 | 選填（「今天不來」只是幫教練估人數，不扣堂、不罰） | **必填**：召集 → 回覆可／不可 → 截止 → 確定名單 |
| 當日 | 教練在 LIFF 點名＝簽到＝扣 1 堂 | 依確定名單點名 |
| 未出席 | 不扣堂、不記違規 | 依球團政策（待決定） |

**相對於現有程式的簡化：**
- 訓練不再需要先報名才能點名；教練可直接把當天出現的孩子加入點名。
- 取消 24 小時取消鎖、「無故缺席」扣堂等訓練規則（目前程式已設為 0，但 UI 與流程仍以報名為前提）。
- **餘額不足時不擋點名**：允許堂數變成負數（＝欠堂），自動產生工作清單「某某欠 1 堂，請提醒續購」。實體卡模式本來就是先上課後補買。
- `special` 扣 2 堂等規則改為設定表（`debit_policies`，含生效日），不寫死在 SQL 函式。

### 3.4 帳務（堂數錢包、收款、對帳）

```
購買意向（家長在 LIFF 選方案）
   ↓
收款紀錄 payments：轉帳（截圖、金額、末五碼、日期）或現金（收據號、收款人）
   ↓ 對帳（人工確認，或匯入銀行對帳單自動配對）
入帳：堂數錢包 +N，帳本寫 purchase（記下當時價格）
   ↓
每次簽到：帳本寫 attend_debit −1
   ↓
例外：退費 refund、管理員調整 admin_adjust、沖銷 reversal（用原單價）
```

| 需求 | 設計 |
| --- | --- |
| 10／20／30 堂方案 | 現有 `session_packages`；申報時記下價格與堂數（修正改價 bug） |
| 無效期 | 不設到期；帳本保留 `expiry` 類型但預設不用 |
| 數位課程卡 | LIFF 卡片頁＝帳本的家長視圖：購買日、每次上課日期、剩餘堂數 |
| 轉帳 | 家長上傳截圖 → AI 擷取金額、末五碼、日期 → 預填 → 管理員一鍵核准 |
| 現金 | 管理員／教練在 LIFF 登記「收現金」→ 系統產生收據編號 → **每日現金日結**（收款人、金額、筆數），日結後鎖定 |
| 對帳 | P1：匯入網銀對帳單 CSV，按金額＋末五碼＋日期自動配對，人工確認例外 |
| 一次幫兩個孩子付款 | 收款紀錄掛家戶，再分配到各孩子的錢包 |
| 舊資料轉移 | 上線時把實體卡剩餘堂數一次性匯入，帳本記 `opening_balance` |

### 3.5 賽事

沿用現有比賽模型（比賽＝場次＋比賽資訊），加上：

| 階段 | 系統動作 | 人工動作 |
| --- | --- | --- |
| 1. 匯入 | 貼上賽會網址、PDF 或圖片 → AI 擷取賽程（§4） | 確認 |
| 2. 召集 | 選隊伍 → 系統對該隊家長推送 LINE 召集卡片（含截止時間） | 按「發送」 |
| 3. 追蹤 | 截止前 24 小時自動提醒未回覆者；工作清單顯示「U10 尚有 3 人未回覆」 | — |
| 4. 定名單 | 依回覆產生建議名單 | 教練確認 |
| 5. 佈達 | AI 依名單、集合時間、地點、裝備擬三語通知 | 確認後發送；同步更新行事曆 |
| 6. 賽後 | 比分、戰績上官網 | 輸入比分 |
| 7. 報名賽會 | 匯出名冊＋照片 ZIP（現有） | 上傳到賽會系統 |

### 3.6 溝通

| 類型 | 管道 | 說明 |
| --- | --- | --- |
| 廣播（停課、賽程變更） | LINE OA 群發（依梯隊分眾）＋ 既有 LINE 群組貼文 | AI 擬三語稿，人確認後發送 |
| 個人通知（入帳、欠堂、召集、提醒） | LINE OA 個別推播 | 由 outbox 事件觸發 |
| 教練訊息翻譯 | LIFF 或 LINE 對話 | 日本教練用日文寫 → AI 翻繁中（＋英文）→ 工作人員抽查或直接發 |
| 家長提問 | LINE 對話 | AI 先分類與草擬回覆（§4） |

LINE OA 的訊息費用依方案與則數計算，群發會快速消耗額度。**請在申請時查最新價目**，再決定哪些廣播走 OA、哪些留在群組。

### 3.7 內容（官網 CMS 與潛在學員）

| 實體 | 說明 |
| --- | --- |
| `site_posts` | 消息：三語欄位（繁中必填，日文和英文可空、自動退回繁中）、封面圖、發布狀態 |
| `site_coaches` | 教練：姓名、證照、照片、介紹（三語） |

AI 可協助：管理員輸入一句中文 → 擬三語消息稿。

### 3.8 工作清單（Task Inbox）——本藍圖的核心

所有「需要人處理的事」集中在一個清單，管理員和教練打開後台或 LIFF 的第一頁就看到。

```
tasks
  id, kind, title, due_at, assignee_role / assignee_id,
  entity_type, entity_id, status (open / snoozed / done / dismissed),
  source (rule / ai / manual), created_at, done_at, done_by
```

**系統自動產生的任務（規則）：**

| 任務 | 觸發 | 指派 |
| --- | --- | --- |
| 匯款待確認 | 家長送出繳費回報 | 管理員 |
| 現金待日結 | 當日有現金收款且 22:00 前未日結 | 收款人 |
| 欠堂提醒 | 錢包 ≤ 0 | 管理員（可一鍵發 LINE 提醒） |
| 堂數快用完 | 錢包 ≤ 2 | 自動發家長通知，不需人工 |
| 賽事召集未回覆 | 截止前 24 小時仍有人未回覆 | 自動提醒；截止後仍未回覆 → 工作人員 |
| 賽事名單待確認 | 回覆截止 | 教練 |
| 賽會報名截止 | 比賽報名截止日前 3 天 | 管理員 |
| 綁定待審核 | 家長申請（邀請碼模式下大幅減少） | 管理員 |
| 新潛在學員 | 官網表單送出 | 管理員 |
| 翻譯待確認 | AI 翻譯信心低，或內容涉及金錢、傷病 | 工作人員 |
| 家長訊息待回覆 | AI 判斷需要人工 | 工作人員 |
| 換季升組 | 8/1 | 管理員 |

**原則：** 能自動完成且無風險的就自動做（例如「堂數快用完」通知），只把需要判斷的事留在清單上。這就是**例外管理**：工作人員只處理例外，不處理常態。

### 3.9 稽核與事件

`audit_log` 一張表：誰、做了什麼、哪筆資料、改前／改後、時間。每個管理員 RPC 內寫入；同表加 `processed_at` 欄位兼作 outbox，供 LINE 通知與工作清單消費。不需要訊息佇列。

## 4. AI 助理

### 4.1 原則

1. **AI 擬稿、人確認。** 金流入帳、對外群發、名單確定，一律要人按確認。
2. **AI 不碰資料庫權限。** AI 只產生草稿或結構化資料，寫入仍走現有 RPC 與 RLS。
3. **最少個資。** 送給模型的內容只放必要欄位；不送證件、醫療資料。截圖處理完即可刪除原檔（只留擷取結果與縮圖）。
4. **每一次 AI 呼叫都記錄**（輸入摘要、輸出、模型、成本、誰確認），寫入 `ai_jobs`。

### 4.2 功能清單

| # | 功能 | 輸入 → 輸出 | 人工確認點 | 優先 |
| --- | --- | --- | --- | --- |
| A1 | 教練訊息翻譯（日 ↔ 繁中，加英文） | 文字 → 三語文字＋「需人工確認」旗標（涉及金錢、傷病、時間變更時） | 有旗標才進工作清單 | P0 |
| A2 | 公告擬稿 | 一句話＋場次資料 → 三語 LINE 文案 | 發送前確認 | P0 |
| A3 | 轉帳截圖擷取 | 圖片 → `{金額, 末五碼, 轉帳日期, 銀行}` | 管理員核准入帳 | P1 |
| A4 | 賽程擷取 | 賽會網址、PDF、圖片 → 比賽清單（日期、時間、對手、場地、組別） | 預覽後確認（取代目前的規則式解析，讓「AI 擷取」名副其實） | P1 |
| A5 | 家長訊息分流 | LINE 訊息 → 分類（請假、堂數查詢、繳費、賽事、其他）＋草擬回覆 | 查詢類（堂數、下次上課時間）可直接回覆；其餘進工作清單 | P1 |
| A6 | 評估回饋翻譯 | 日本教練的評估評語 → 家長語言 | 教練或工作人員抽查 | P1 |
| A7 | 每週營運摘要 | 本週出席、收款、欠堂、未回覆 → 一段文字報告推給管理員 | 無（唯讀） | P2 |

### 4.3 實作要點（Claude API）

- **SDK：** `@anthropic-ai/sdk`，只在 server 端（Server Action、Route Handler、Vercel Cron）呼叫；API key 放 Vercel 環境變數，絕不進 `NEXT_PUBLIC_*`。
- **模型：** 預設 `claude-opus-5-5`。是否在大量、簡單的路徑（例如 A5 分流）改用較便宜的模型，是之後依實際成本與品質由 Victor 決定的事，先量測再調整。
- **結構化輸出：** A3、A4、A5 用 `output_config.format`（JSON schema）取得固定格式，再用現有的 parse／validate 函式檢查，失敗就進工作清單，不硬寫入。
- **影像與 PDF：** A3、A4 直接送 image／document content block。
- **成本控制：** 翻譯與分流的系統提示（含球團用語對照表，例如 梯隊＝育成クラス、堂數＝回数券）固定放在最前面並開 prompt caching；非即時工作（A7 週報）可走 Batches API。
- **拒答與錯誤：** 檢查 `stop_reason`；API 錯誤或拒答時退回人工流程，不影響業務。
- **用語對照表：** 建一張 `glossary` 表（繁中／日文／英文），由工作人員維護，翻譯時注入提示詞——日本教練的專業術語只要教一次。
